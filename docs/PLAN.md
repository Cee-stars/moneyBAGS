## 0. 結論だけ

- **欲しいものアプリと家計簿を分けない。1つにする。** 過去のお金（家計簿）・いま出ていくお金（サブスク）・未来のお金（欲しいもの）は同じ財布の話で、つなぐと他のアプリにない機能が出る。
- **一番価値があるのはサブスクの「確認サイクル」。** 数字を見せるだけでは人は解約しない。定期的に「続ける／やめる」を選ばせる画面が必要。実取引データで裏付けのある唯一の介入。
- **目標は「支出を減らす」にしない。** 達成できない。「いらないサブスクに払っていない」「固定費を把握している」にする。
- **銀行・カードの自動連携は作らない。** 日本では個人に実質不可能。CSV取込が現実解。
- **置き場所は GitHub Pages。データは iPhone の中だけ。iPhone 専用。¥0。**（2026-10-25 決定）サーバーを持たないので認証も不要。**代わりにバックアップ書き出しが中核機能になる**（iOSが7日でストレージを消すため）。
- **AIコメントは作らない。**（2026-10-28 決定）通信ゼロ・鍵なし・課金なしで全機能が成立する。

## 1. 成功の定義（ここを間違えると設計が歪む）

Grubb et al. (2025) *Journal of Finance* — 英国の銀行で100万人規模の実験。通知で**手数料は17〜19%減った**が、**一般的な支出はほとんど変わらなかった**（"spending is relatively inelastic to these alerts"）。FCA Occasional Paper 40 も同様で、残高通知による節約効果は月あたり£0.28〜0.45。

→ 可視化が効くのは **「個別の・避けられる・忘れがちな出費」**。サブスクの払い続けはまさにこの形。一般的な節約には効かない。

**このアプリの成功条件:**

1. いらないサブスクに払っていない
2. 毎月の固定費がいくらか即答できる
3. 欲しいものを買うまでの距離がわかる

**成功条件にしないもの:** 支出総額が減ること。記録の連続日数。記録率100%。

→ だから **ストリーク・バッジ・レベル・紙吹雪・「えらい！」「3日サボってます」は作らない。** 自閉症の人を対象にしたストリーク機構の研究は1件も存在しないので「良い」「悪い」どちらの主張も根拠がない。評価する言葉そのものを置かない。

## 2. データ設計

### 2.1 お金の持ち方

**2026-10-25 追記:** 保存先が IndexedDB になったので「SQLite に DECIMAL 型は存在しない」という話は直接は当てはまらなくなった。**ただし整数の最小単位で持つという結論は変わらない。** むしろ強まる: IndexedDB は JS の値をそのまま保存するので、小数を入れれば double がそのまま入り、`0.1 + 0.2 !== 0.3` を抱えたまま合計を出すことになる。

**`INTEGER` の最小単位。通貨ごとに exponent を1箇所だけで持つ（JPY=0, USD=2）。カラム名は `_minor` で終える。**

- SQLite に `DECIMAL` は**存在しない**。`NUMERIC(19,4)` と書いても型親和性でしかなく、小数は `REAL`（IEEE-754 double）で黙って保存される。「型名があるから安全」は罠。
- float は不可。`ORDER BY` を変えると合計が変わる台帳は、銀行明細と突き合わせる意味がなくなる。
- JS の安全整数は 2^53−1 ≒ 9×10^15。円で9千兆なので `BigInt` は不要。
- 金額は**常に通貨とセット**で持ち回る。`{ amount_minor: 1200, currency: 'JPY' }`。裸の `1200` を渡さない。
- 一番怖いバグ: JPY を exponent 2 のつもりで `120000` と書く。表示するまで気づかず100倍ずれる。I/O境界に `amountToMinor()` / `minorToDisplay()` を1組だけ置いて防ぐ。
- 割り算（年額→月割り、割り勘）は整数で計算して**最大剰余法**で端数を配る。年額だと最大11円ずれるので、放置せず扱う。

Actual Budget が本番でこれをやっていて、JPY は `decimalPlaces: 0` になっている。

### 2.2 テーブル構成

**保存先は SQLite ではなく IndexedDB**（2026-10-25 の構成変更）。下の「テーブル」は IndexedDB の object store として読む。**型の設計はそのまま有効**で、変わるのは保存の仕組みだけ。SQL が使えないぶん、集計はアプリ側のコードで書く（1人分のデータ量なら問題にならない）。インデックスは object store の index として張る。

```
subscription          契約そのもの（名前だけ。金額も日付も持たない）
  └ subscription_term   条件（期間つき）← トライアル・値上げ・休止・プラン変更が全部ここ
      └ expected_charge   予定された請求（期間を限って実体化）
            ⇕ 突き合わせ
          txn             実際の取引（台帳。1テーブルだけ）

wishlist_item         欲しいもの
  └ wishlist_funding    「このサブスクを解約するとこれが買える」の結び
txn_allocation        App Store の合算請求を複数サブスクに分解
merchant / merchant_alias  CSV取込時の名前の正規化先
```

**なぜ `subscription` に金額を持たせないか。** 金額を上書きすると過去が書き換わる。去年の集計が今日変わるアプリは信用できない。期間つきの `subscription_term` にすると、トライアル（`amount_minor=0`）・値上げ・休止・月額→年額の切り替えが**全部同じ仕組み1つ**で済む。`price_history` テーブルでは「月額から年額に変えた」が表現できない（金額と周期が同時に変わるため）。

**なぜ `expected_charge` を別に持つか。** 「11月3日の1,480円は10月分のNetflixが遅れて来たもの」という判断を**覚えておく場所**が必要。計算で出すだけでは注記できない。`missed`（来るはずが来なかった）も状態として持つ。期間は today−3ヶ月 〜 today+12ヶ月だけ実体化し、それ以上は計算で出す。

**なぜ台帳は1テーブルか。** カード明細は1本の流れ。分けると残高・月次合計・CSV取込が全部 UNION になる。サブスクかどうかは取込後に判明する性質なので、`txn.subscription_id` という nullable な外部キーにする。

### 2.3 31日課金が2月にどうなるか

**要求された日を保存し、計算時に `min(anchor_day, その月の日数)` でクランプする。**

Firefly III のソースで確認（`CalculateXOccurrences.php:73` ほか3箇所で同じ `min()`）。Stripe も同じ挙動で、1月31日アンカーなら **2月28日 → 3月31日 → 4月30日**。

**クランプした値を保存してはいけない。** 保存すると28日に下がったまま戻らず、二度と31日に戻らない。

- `anchor_day = -1` は「月末日」。31日とは**意図が違う**（表示が「毎月末日」か「毎月31日」か変わる）。GnuCash は `PERIOD_END_OF_MONTH` という別の型にしている。
- **k番目の請求日は `(anchor_date, freq, interval_n, k)` の純関数にする。** 前の行から計算しない。これでドリフトが起きず、再生成しても同じ結果になる。
- **RRULE 文字列を保存してはいけない。** RFC 5545 の `FREQ=MONTHLY;BYMONTHDAY=31` は**クランプせず省略する** = 2月・4月・6月・9月・11月を飛ばす。課金の意味として絶対に間違い。語彙（FREQ/INTERVAL/BYMONTHDAY/BYDAY）だけ借りて、カラムに分解して持ち、クランプは自分で実装する。SQL から見えなくなる問題もある。
- 周期は **(基本周期 × 倍数)** に統一。四半期 = `MONTH, 3`、隔週 = `WEEK, 2`。Firefly / GnuCash / Actual が独立に同じ形に収束している。
- 倍数が2以上のときは**位相が必要**。「四半期ごとの15日」は1月/4月/7月/10月か2月/5月/8月/11月か決まらないので、`anchor_date`（最初の実請求日）で決める。

### 2.4 年額サブスクは月割りか一括か

**実際の請求月に一括で保存する。正規化した数字は計算で出す。両方保存しない。**

1. 台帳はカード明細と一致しなければならない。¥11,980/年を¥998×12で持つと11月の合計が明細と合わず、アプリの唯一の外部チェックが失われる。
2. 端数が漏れる。11,980 ÷ 12 = 998.33 → 998×12 = 11,976。年4円の漏れ。JPY は exponent 0 なので小数部に隠せない。
3. 2つの数字は**別の問いに答える**。「11月に払えるか」= 一括。「Adobe は Figma と比べて高いか」= 年額換算。

**正規化の正は「年額」にする。** 月額 = 年額 ÷ 12 を表示の最後だけで計算。月額を個別に丸めてから合計すると、合計がずれる。

YNAB の True Expenses も同じ分離で、月割りは**予算レイヤーの概念で、台帳レイヤーではない**。

### 2.5 予定と実際の突き合わせ

**自動で台帳に書き込まない。予測して、来たら突き合わせる。**

Actual Budget のデフォルトが `posts_transaction = 0`（= 予測して突き合わせ）。GnuCash も20年前から `auto_create` と `auto_notify` を分けている。Firefly III は cron で自動投入するが、ドキュメント自身が cron 運用の注意を大きく書いている。

CSV取込する前提だと自動投入は純粋に損。実際の請求はCSVで来るので、1件の請求に2行できて必ず重複排除が必要になる。手間が増えて得が何もない。

```
未突合の txn について:
  候補 = expected_charge で
      state が forecast / due / missed
      かつ 店名が一致
      かつ txn.date が due_on ± 5日
      かつ 金額が ±7.5% 以内
  候補がちょうど1件 → 結びつけて matched
  それ以外 → 未突合のまま確認キューに出す
```

±2日 / ±7.5% は Actual Budget の実装値（ソースで確認）。**日本のカードは「月末締め・翌月払い」で計上日が請求日から数日ずれるので±5日に広げる。**

重複・ドリフト対策:

| 失敗 | 対策 |
|---|---|
| 重複 | `expected_charge` に `UNIQUE (subscription_id, due_on)`。生成は `INSERT … ON CONFLICT DO NOTHING` にして冪等にする（ページ表示ごとに走らせても安全）。`txn` には `UNIQUE (account_id, import_hash)` でCSV再取込も冪等に |
| ドリフト | k番目を純関数で計算（§2.3） |
| 来なかった請求 | 猶予後に `missed`。**自動削除も、黙って繰り越しもしない** |
| 予測が合計に混ざる | 予測は `expected_charge`、事実は `txn`。構造的に混ざらない |
| **値上げに気づかない** | 店名と日付は合うのに金額が band を外れた取引は**このアプリで一番価値のあるイベント**。「Netflixが1,480円→1,590円になりました。条件を更新しますか？」として出し、期間を閉じて新しい期間を開く。スキーマからタダで出てくる |
| 日付の壊れ | 日付は `TEXT 'YYYY-MM-DD'` で保存。epoch も `Date` のUTC往復も使わない。請求日は瞬間ではなく暦日。Firefly III は後から `date_tz` カラムを足す移行が必要になった |

### 2.6 外貨サブスク（USD建て・円払い）

**最小限で対応する。FXレート取得の仕組みは作らない。**

日本のカードだと `円 = USD額 × ブランド参照レート × (1 + 海外事務手数料)`。手数料は発行会社で1.6%〜3.85%（エポスは2025年7月改定で3.85%）。参照レートは全部公開されていない。**適用レートは売上確定日基準なので、同じUSD価格でも毎月円額が変わる。**

- `txn.amount_minor` = 円（事実）、`txn.orig_amount_minor` / `orig_currency` = USD（意図）、`fx_rate_micro` = 2つから**計算で出す**（発行会社の手数料が自動で含まれる）
- 予測は**そのサブスク自身の過去の実効レート**を使う。市場レートより正確で、API呼び出しがゼロ
- 外貨サブスクは許容幅を広げる（±15%）。±7.5%だと毎月確認キューに入って、確認をやめる
- USD額が変わらないのに `fx_rate_micro` が跳ねたら、それは値上げではなく為替。区別できるのは両方持っているから

## 3. 技術構成

**2026-10-25 決定: GitHub Pages + 端末内保存。iPhone 専用。サーバーなし。¥0。**
これ以前に書いてあった VPS 案・Cloudflare 案は両方とも採らない。

### 3.1 置き場所

| 項目 | 決定 |
|---|---|
| 配信 | **GitHub Pages**（静的ファイルのみ）。`main` にプッシュすると GitHub Actions が自動デプロイ |
| アプリの形 | Next.js の静的書き出し（`output: "export"`）＋ PWA。ホーム画面に追加して使う |
| データの置き場所 | **iPhone の中（IndexedDB）だけ。** サーバーに送らない |
| 写真 | 同じく IndexedDB に Blob で持つ |
| 認証 | **不要。** データが端末から出ないので守る通信経路がない |
| 費用 | ¥0。クレジットカード登録も不要 |
| 対象端末 | **iPhone 1台のみ。** PC やスマホ間の同期はしない |

**この構成の長所は、privacy が構造的に最強になること。** VPS 案は自分のディスク、Cloudflare 案は Cloudflare のディスクにデータが載るが、この構成では**家計データが端末から1バイトも出ない。** 認証もサーバーの運用もバックアップ契約も、守るものがないので全部消える。

**短所は1つだけ、しかし重い: データが1箇所にしかない。**

### 3.2 データ消失リスクと、その対策（この構成の最重要項目）

**iOS は7日間使わないとスクリプトから書けるストレージ（IndexedDB・localStorage・Service Worker）を削除する**（iOS 13.4以降）。Apple の WebKit チームは「ホーム画面に追加したアプリは独自の使用日数カウンタを持ち、first-party のデータは削除されないと考えている」と述べているが、**ホーム画面アプリでも消えたという WebKit のバグ報告が複数ある**（iOS 15.0.2 で IndexedDB ごと消失、iOS 15.3 で期間内に開いていたのに Cookie が消去）。

さらに `navigator.storage.persist()` は Safari ではプロンプトを出さず利用履歴から自動で許可/不許可が決まり、**ITP との関係について公式な記述が見つからない。**

**つまり端末内保存を唯一の正としてはいけない。** 対策を仕様に組み込む:

1. **起動ごとに `navigator.storage.persist()` を要求する。** 結果を画面に出して本人が見られるようにする（実装済み・プレースホルダ画面の下部）
2. **バックアップの書き出しを「おまけ」ではなく中核機能にする。** 1タップで全データをJSONファイルにして、iOS の共有シートから iCloud Drive に保存できる形にする
3. **最後にバックアップした日を画面に常時出す。** 7日を超えたら「7日を超えました」と事実で表示する（責めない。§4.6の方針どおり）
4. **写真はバックアップを分ける。** 写真込みのJSONは重くなるので、データ本体と写真を別ファイルにする
5. **読み込み（復元）も同じ重さで作る。** 書き出せても読み込めないバックアップは意味がない

**この5つは段1と同時に作る。** 機能を足してから後付けにしない。データが消えてから作っても遅い。

### 3.4 Next.js とビルドの設定（実装済み）

- **Next.js 16.4.3。** 当初 16.4.0 を入れたが `npm audit` が critical を報告した（画像最適化APIのSVG経由RCE、Server Actions のDoS、`use cache` のRCE）。脆弱な範囲は 16.0.0〜16.4.0 なので 16.4.3 に上げて**脆弱性ゼロ**にした。なお3件とも静的書き出しには存在しないサーバー機能なので、実害はもともとなかった
- **`output: "export"` + `basePath: "/moneyBAGS"`。** GitHub Pages のプロジェクトページは `https://<user>.github.io/<repo>/` で配信されるため basePath が必要。独自ドメインに移すときは `NEXT_PUBLIC_BASE_PATH=""` で上書きできるようにしてある
- **`images.unoptimized: true`。** 画像最適化はサーバー機能なので静的書き出しでは使えない
- **`public/.nojekyll`。** これがないと GitHub Pages の Jekyll が `_next/` を削除して全部壊れる
- **`app/manifest.ts` に `export const dynamic = "force-static"`。** 静的書き出しでは必須。これがないとビルドが失敗する（実際に失敗した）
- **フォントは iPhone 内蔵の Hiragino Sans。** `-apple-system, "Hiragino Sans", "Hiragino Kaku Gothic ProN"` の順。Google Fonts を読まないので**通信ゼロ・オフラインでも字が崩れない**。日本語のWebフォントは数MBあるので、iPhone 専用ならこれが最善
- **`maximumScale: 5` / `userScalable: true`。** 拡大を禁止しない（視覚のアクセシビリティ）。PWA でよく `maximumScale: 1` にされるが、やらない
- **`viewportFit: "cover"` と `env(safe-area-inset-*)`。** ノッチとホームバーを避ける
- **Service Worker はまだ入れていない。** オフライン対応が必要になってから `@serwist/next` を足す（`next-pwa` は2022年から更新が止まっているので使わない）。マニフェストだけでもホーム画面追加・単独ウィンドウは動く


## 4. 画面と機能

プレビュー: https://claude.ai/artifact/B3o8PePPcKaho1aJKQqMfJ （6画面・数字はダミー）

### 4.1 サブスクの確認サイクル ← 最優先

Einav / Klopack / Mahoney "Selling Subscriptions"（FTCに提出）— 決済カードネットワークの実取引データ。**カードが期限切れで再発行され「続けるか」の能動的決定を強制されると、解約が急増する**（対象10サービス全部で）。この摩擦があることで事業者の売上は平均で約2倍。現金前借りをした消費者（金融リテラシーの代理指標）で不注意が大きい。

**情報だけでは解約されない。決定を強制されると解約される。** この報告書で唯一、取引レベルの実データに裏付けのある介入。

実装:
- 各サブスクに `最終確認日` を持つ。設定した間隔（既定3ヶ月）を過ぎたら `要確認` になり、ホームに「3件が確認待ち」が出る
- 1件ずつ**二択**: 「続ける」／「解約を検討する」。**「あとで」や「OK」は置かない。** 決めさせることが機構そのもの
- 確認すると日付が更新されて状態を抜ける。**カード期限切れを人工的に再現している**
- **件数を区切って終わらせる。** 「3件、終わり」。終わらないキューにしない
- 「解約を検討する」を選んでも**アプリは勝手に解約しない**（決済経路にいないので、できないしフリをしてもいけない）。検討リストに移るだけ

### 4.2 サブスク表示は年額を主役にする

Gourville (1998) *JCR* の "pennies-a-day" — 一括費用を小さな定期額に言い換えると好意的に評価される（$350/年 → $1/日）。機構は**比較対象の想起**。売り手はこれを使って安く見せる。

**逆に回す。** 月額980円ではなく**年額11,760円**を主役にする。合計も年額を見出しにする。

境界条件として、**元の金額が大きくなると効果は弱まり反転する**（Gourville 自身）。そして**逆向きの利用は誰も検証していない**ので、方向だけ採用して効果量は期待しない。

あわせて:
- **契約から今までに払った合計**を各行に出す（Netflix 2年3ヶ月で42,930円）。「見えないものを見えるようにする」の実体
- **次の支払日で並べる**（Bobby から）。リストがタイムラインになる
- 残り日数をバーで（Costly から）。日付より一目でわかる
- 「¥0」と「未記録」は**別の見た目にする**。同じに見せているアプリが多い

### 4.3 記録は金額だけ必須

自己追跡研究で一番強い知見: **「データ収集の負担が大きい領域ほど、アプリは捨てられる」**（Epstein）。

- **必須は金額だけ。** 分類・日付・メモは既定値を入れて後から直せる。**分類なしで金額が正しい記録は、記録がないよりはるかに価値がある**
- 分類はタップチップで、**前回使った値を既定**にし、自分の使用頻度順に並べる
- 保存したら**閉じずに留まる**。金額だけ消して分類と日付は維持、金額欄に再フォーカス。「もう1件」と「取り消し」を出す。記録はまとめて起きる
- 日付は今日が既定。昨日は1タップ。それより前は折りたたみの奥
- **全角数字・カンマ・「円」「¥」を黙って受け入れる。** 日本語IMEは全角数字を常時生成するので、弾くのは自分で作ったエラー源。入力時に正規化する
- **下書きは1打鍵ごとに保存。** アプリを閉じても、強制終了しても、再起動しても残る。実際に効くのはこれ
- 入力中に赤くしない。検証は blur か送信時。打っている途中の赤は偽のエラーで、赤を無視する癖がつく

**記録漏れを前提に設計する。** 「10月は13日すぎて11日分記録しました。2日分記録していないので実際はもう少し多いかもしれません」と**正直に出す**。完全であるフリをしない。そして**「8日分記録されていません」と催促しない。**

### 4.4 欲しいもの: 「あと いくら」と理由

- **「あと21,400円」を一番大きく出す。** パーセントより残額が判断に使える（パーセントも併記するが主役にしない）
- 月いくら貯めるとあと何ヶ月か
- **「買う理由」「買わない理由」を必須入力にする。** ミシガン大の研究: **10分の受動的な待ち時間は効果が統計的に有意でなかった**（待っている間も買い物を続けるため）。**25時間の遅延は効いた。** そして**3分半かけて賛否を書き出すのは、短時間でも効いた**。→ 待たせるだけでは意味がない。**書かせる**
- 待機期間の下限は**24時間以上**（研究が支持する下限）。日数は設定にする。30日は根拠がない私の思いつきだった
- **`wishlist_funding`** — 「Netflix（月1,590円）と Adobe（年6,480円）を解約すると、42,000円のヘッドホンが20ヶ月で買える」。逆向きにも「この42,000円の買い物は、今のサブスク支出2.0年分」。**この2つの数字はどのアプリでも今は出せない**（突き合わせ済み台帳・サブスク予測・値段つき欲しいものリストを同じDBに持つアプリが存在しないため）

#### 項目ごとの色

**色の役割は「見分けること」だけ。状態や良し悪しは表さない。** 研究で避けるべきとされたのは「赤緑で予算の良し悪しを示す」ような**状態の色**で、識別のための色は別の話。品名のテキストは常に出るので、色が見えなくても情報は失われない（WCAG 1.4.1）。

6色を固定順で使う。検証スクリプトで全項目通過:

| 枠 | 色 | 用途 |
|---|---|---|
| 1 | `#2B6CB0` 青 | 順位チップ（白文字）、進捗バー、写真枠の枠線と薄い地 |
| 2 | `#A84E1C` 橙 | 同 |
| 3 | `#00806A` 緑 | 同 |
| 4 | `#8F6B00` 金 | 同 |
| 5 | `#6E4FC4` 紫 | 同 |
| 6 | `#B3436E` 桃 | 同 |

検証結果: 明度帯すべて内 ／ 彩度下限クリア ／ **隣接色の色覚異常での識別 ΔE 9.7**（目標8以上）／ 通常視 ΔE 15.1（下限15）／ 背景とのコントラスト全色3:1以上。加えて**白文字が全色 4.5:1 以上**（金と橙は当初 3.47 / 4.44 で足りず、暗くして通した）。

- **パーセントの文字と金額は色を着けない。** 文字は文字の色、色は印（バー・チップ・写真枠）が担う。色付き文字は読みにくくなるだけで識別には寄与しない
- 7件目以降は色を繰り返す。グラフの系列と違い、項目の識別色の巡回は問題ない（カレンダーの色と同じ扱い）
- 色は**あとから変更できる**ようにする（既定は追加順）
- **ダークモードは作らない**（2026-10-13 決定）。暗い背景用に6色を取り直して再検証する作業が丸ごと不要になる。明るい配色1本で、背景の色味だけ数種類から選べるようにする

#### 写真

欲しいものに写真を1枚つけられるようにする。実物を見ると判断しやすいのと、何を指しているかが品名より速く分かる。

プレビューでは**枠だけの仮置き**（実在しない商品写真を捏造しないため）。3件は「写真あり」の枠、1件は「写真を追加」の状態を出してある。

実装側で決めること:

- **画像は IndexedDB に Blob で持つ。** サーバーがないので置き場所は端末内だけ。**写真はバックアップを本体と別ファイルにする**（JSONが重くなるため・§3.2）
- **変換はブラウザ側でやる。** サーバーがないので他に選択肢がない。`canvas` で WebP か JPEG に縮小・変換して保存する。**原寸は保存しない**（端末の容量は有限で、iOSのストレージ上限も読めないため）
- **iPhone から来るのは HEIC。** ただし iPhone 専用かつ Safari なら `canvas` でデコードできる見込みが高い。**実機で確認してから** 必要なら libheif の WebAssembly 版をフォールバックに積む（先に積むと数百KB無駄になる）
- **EXIF の回転情報を適用して焼き込む。** しないと横向きで表示される
- **EXIF の位置情報は捨てる。** 家で撮った写真に自宅の座標が入る。ブラウザで再描画すれば EXIF ごと落ちるので、変換が実質そのまま対策になる
- サムネイル（160px 程度）と表示用（800px 程度）の2枚を持つ
- 上限サイズを決めて弾く（変換後1枚2MBなど）
- 写真は任意。**なくても全部動く**（記録の必須項目は金額だけという方針と同じ）

### 4.5 AIコメント — 作らない（2026-10-28 決定）

**本人の決定により、AIコメント機能は作らない。** 以下は判断の記録。

- サーバーを持たない構成なので、Claude API の鍵を隠す場所がない。残る案は「自分のキーを端末内に置いてブラウザから直接呼ぶ」だけだった
- その案も成立はするが、キー管理・課金・通信の発生という3つが1人用アプリに乗ってくる
- **そして数字の表示とサブスク確認サイクルは、AIコメントなしで全部成立する。** §1 の成功条件（いらないサブスクに払っていない／固定費を把握している／欲しいものまでの距離がわかる）はどれもAIを必要としない

**代わりに何を置くか。** コメントがあった場所（ホーム画面の最上部）には **「確認待ちのサブスク」** と **「今月の残り」** を置く。どちらも事実の表示で、読んで判断できる。AIの文章がないぶん、画面は静かになり、通信もゼロになる。

数字から文章を組み立てる処理そのものは、**テンプレートで書けるものに限ってアプリ内で作る余地がある**（「先月の同じ日より4,100円多い」など、計算と差し替えだけで出る文）。ただしこれは段1〜4が動いてから検討する。**AIは使わない。**

### 4.6 色・動き・音

- **純白の背景と純黒の文字を使わない。** WCAG は**最低値を定めていて上限がなく、彩度については何も言っていない**ので、AA を満たしたまま感覚的に過負荷な配色が作れる。`#000` on `#FFF` は最大限準拠かつ最悪
- **落とすのは彩度と輝度。コントラスト比は落とさない。** `#4a5568` は白地で 7.0:1（AAA）の落ち着いたグレー
- **色だけで意味を運ばない**（WCAG 1.4.1）。予算超過は「超過 +3,200円」と文字で書く
- **赤緑を予算の主要な意味軸にしない。** 罪悪感を誘発する赤緑インジケータは離脱要因として独立に指摘されている。グレー→アンバーのランプにする
- `prefers-reduced-motion: reduce` を尊重。**グラフの描画アニメーションは既定でなし**（毎回開くたびに動くことになる）。数字のカウントアップもなし（動きであり、かつ**一瞬まちがった数字が画面に出る**）
- **音は一切なし。** 保存音も触覚＋音もなし
- **招かれていないモーダルをゼロにする。** 評価依頼、Tips、「ご存知ですか」、「3日記録していません」— 全部なし。アプリから言いたいことは、ダッシュボードの常設領域に置いて、本人が読みたいときに読む。push ではなく pull
- 読み込み中に高さが変わらない。読んだ内容が押し下げられない
- **開いたとき毎回同じ画面**（どの画面かは設定）

### 4.7 設定項目

研究が個人差で割れている、または根拠が見つからなかった箇所。**既定値は私の推測で、知見ではない。**

| 設定 | 選択肢 | 既定 |
|---|---|---|
| 背景の色味 | 暖かい白 / 冷たい白 / 薄緑（**暗い配色は作らない**） | 暖かい白 |
| アニメーションを減らす | on / off（OS設定とは別に） | on |
| **文字の大きさ** | 標準 / 大きい / もっと大きい（行間も一緒に変わる） | 標準 |
| 情報量 | 標準 / 詳細（**同じ情報の詰め方を変えるだけ。見られる情報は変えない**） | 標準 |
| 記録率の表示 | on / off | on |
| 確認文の言い方を毎回変える | on / off | **off** |
| 開いたときの画面 | ホーム / サブスク / 記録 | ホーム |
| サブスク確認の間隔 | 1 / 3 / 6ヶ月 | 3ヶ月 |
| 通知 | 種類ごと、全部オフが既定 | 全部オフ |
| 欲しいものの待機下限 | 24h / 48h / 72h | 24h |
| サブスクの金額表示 | 年額優先 / 月額優先 | 年額優先 |

**自閉症の人を1つの型に当てはめない。** 感覚特性の非典型性は推定60〜97%で、3〜6のサブタイプに分かれ、**同じ人が1つの感覚で過敏で別の感覚で鈍麻でありうる**。1人用アプリなので、**自分で数週間試して調整できる**のは市販アプリにない利点。

## 4.8 自閉特性に合わせて入れる機能（2026-10-28 決定）

本人と1つずつ確認して決めた。**「自閉症向け」を一枚岩にしない**のが前提。感覚特性の非典型性は推定60〜97%、3〜6のサブタイプに分かれ、同じ人が1つの感覚で過敏・別の感覚で鈍麻でありうる（Uljarević et al. 2017 ほか）。だから下記も「この人に合うか」は使ってみて判断する。

### 入れる

**(1) 解約ページのURLを保存する** ★実装が一番安く、効果が一番大きい

「解約する」と決めた直後に「どこで解約するんだっけ」で止まるのが実行機能の壁。決断でエネルギーを使い切った直後に検索という新しいタスクが来る。サブスクごとに `cancel_url` を1回保存しておき、確認画面から直接飛べるようにする。**カラム1つ追加するだけ。**

**(2) 「今日はこれで終わり」で閉じられる画面**

調査の一文: **「完了できることが機能である」**。常に何かやり残しがあるアプリはルーティンを支えるのと逆。

- 1日1回の画面があり、記録し終わったら「今日はこれで終わり」で閉じられる
- サブスク確認は「3件、終わり」で終わる（実装済みの設計）
- **終わらないキューを作らない。** 常時点灯のバッジも置かない（2回目の提示で注意は急落する）

根拠は物理空間の研究（感覚の質・理解しやすさ・予測可能性の三要素）からの類推だが、COGA とウェブ調査も同じ結論に収束していた。

**(3) iOSのショートカットで「決まった時刻に開く」**

プッシュ通知は iOS では信頼できないので使わない。代わりに**OSと戦わずOSを使う**。「毎晩21時に moneyBAGS を開く」オートメーションを本人が「ショートカット」アプリで組む。**アプリ側の実装はゼロ**で、必要なのは手順の説明だけ。アプリから割り込まない（§4.6 の方針と一致）。

**(4) 「あとで分類する」を正式な状態にする**

金額は分かるが分類を決められない場面で、適当に選ばせない。「あとで分類する」を**ちゃんとした状態として持つ**。間違った分類が入るより、未分類と分かっているほうが価値が高い。**そして催促しない。**「¥0 と未記録を別の見た目にする」（§1.3）の延長。

**(6) サブスクを「件数」で見る**

日本の就労移行支援事業者のコラムに出てきた知見で、**ASD特性に対しては「金額」ではなく「個数」で制限するほうが機能する**という実務的な話。本人も「件数という考え方は初めてで効きそう」とのこと。

**根拠は弱い**（支援機関のブログで、研究ではない）。そして本人も「まだわからない」という状態。なので**こう分ける:**

- **件数の表示は常に出す。** 「いま契約しているサブスク: 7件」。これはタダで、害がない
- **上限の数字は任意。** 設定しなければ上限なしで動く。**今決めなくていい**
- 上限を設定した場合、超えても**ブロックしない**。「上限8件を超えています（9件）」と事実で出すだけ。§1 の「罪悪感の仕掛けを作らない」方針を崩さない

### 入れない

**(5) if-thenプラン（実行意図）を保存する → 作らない**（本人の決定）

参考までに記録しておくと、Gollwitzer & Sheeran (2006) は94件の検証で d=.65 だが、**これは出版バイアス補正前**。補正後 d=0.35、さらに調整して 0.15 という報告があり、**長期的で難しい目標では効果が小さい**とされる。期待しすぎないほうがよい類の介入だった。

### 文字の大きさ（本人から一任されたので決めた）

**3段階の1つのつまみにする。標準 / 大きい / もっと大きい。既定は標準。**

決めた理由:

- **スライダーにしない。** 無段階だと調整そのものが作業になり、終わりが来ない。3択なら決めて閉じられる（§4.8(2) と同じ考え）
- **文字サイズと行間を別々のつまみにしない。** 大きくすると行間も一緒に広がる（1.85 → 1.95 → 2.05）。2つ並べると組み合わせが9通りになり、選ぶコストが上がるだけ
- **全部 rem 基準でスケールさせる。** 金額の大きい数字から12pxの補助文字まで、1つの倍率（1 / 1.15 / 1.3）で一緒に動く。個別に指定した px が残っていると、大きくしたとき一部だけ取り残されて逆に読みにくくなる
- **ピンチでの拡大も禁止しない。** `maximumScale: 5`、`userScalable: true` のまま。ただし拡大は横スクロールが出るので、**まず文字サイズ設定で足りるようにする**のが本筋
- **W3C 目標8「適応とパーソナライズ」**がまさにこれを求めている（font size, line height, margins, contrast の設定）

**トークン層に先に入れる。** 調査でも「最初に正しくやるのが一番安く、後付けが一番高い」と指摘されていた箇所。

## 5. やらないこと

| やらない | 理由 |
|---|---|
| **銀行・カードの自動連携** | 日本では口座情報の取得・提供は**電子決済等代行業（第二号）**で、**財務局への登録**が必要。審査は体制まで見るし、**銀行ごとに個別契約**が要る。Moneytree LINK は法人営業のみで公開価格・セルフサインアップ・サンドボックスが存在しない。個人が通せる種類のものではない（禁止条文を読んだわけではないので「法的に不可能」とは言わないが、実務上届かない） |
| レシートOCR | 訂正作業が手入力より面倒という報告がある。手入力を2タップにするほうが確実 |
| ストリーク・バッジ・レベル | 記録という代理指標を最適化する。何もない日は記録することがないので、素朴なストリークは**良い行動を罰する**か無駄タップを要求する。自閉症の人を対象にした研究は1件も存在しない |
| 検出されたサブスクの自動登録 | **提案はする、自動確定はしない。** 偽陽性のサブスクが黙って入ると、機能不足よりも速く合計への信頼が壊れる |
| FXレート取得の仕組み | そのサブスク自身の実効レートのほうが正確で、API も鍵もジョブも不要 |
| 共有・複数ユーザー・認証 | 1人用。**認証そのものが不要**（データが端末から出ないので守る通信経路がない）。公開されるのは誰が見ても無意味な空のアプリだけ |
| PC・他端末との同期 | iPhone 1台のみ。サーバーがないので同期する相手がいない。移行はバックアップJSONを手で運ぶ |
| プッシュ通知 | iOS の Web Push は信頼できない。アプリを開いたときのバッジ表示にする → §3.3 |
| **ダークモード** | 2026-10-13 決定。明るい配色1本。識別用6色を暗い背景で取り直して再検証する手間、`prefers-color-scheme` の分岐、2系統のトークン管理が全部なくなる。背景の色味は明るい範囲で数種類から選べるようにする |

| **3** | **確認サイクル**（二択・件数を区切る） | 唯一実データの裏付けがある介入。ここが本体 |
| **4** | 欲しいもの（あと いくら・理由の必須入力・24時間以上の待機）＋ `wishlist_funding` | 他にないのはここ |
| **5** | **削除**（AIコメントは作らない・§4.5）。空き番は詰めず、以降の段番号は変えない | — |
| **6** | CSV取込（Shift_JIS 前提・取込元ごとのプロファイル・`import_hash` で冪等）＋ 継続課金の検出（提案のみ） | 手入力が続かなかった場合の保険 |
| **7** | 実機確認（ホーム画面追加・保存の永続化・HEIC）・支払い前バッジ・Service Worker（必要なら） | 段1が動いてから。**デプロイ設定は段0で済んでいる** |

**段6の検出アルゴリズム**（成熟したOSSライブラリは存在しない。自分で200行ほど）:
1. **`normalize('NFKC')` を最初に。** 日本のカードCSVは半角カナ（`ｱﾏｿﾞﾝ`）・全角（`アマゾン`）・全角英数（`ＡＭＡＺＯＮ`）が混在する。これをやらないと同じ店が3つに分裂して検出が黙って失敗する
2. カタカナ↔ラテンは正規化では解けない（`ネットフリックス` vs `NETFLIX.COM`）→ 学習する `merchant_alias` テーブル。1回確認すれば永続
3. `AMAZON DOWNLOADS` / `PAYPAL *` / `APPLE COM BILL` / `GOOGLE *` などの接頭辞と、`（カ`・店舗コード・`＊` を除去
4. 間隔のクラスタリング。**月次は「30日±4」より「同じ日（または両方月末クランプ）」を優先**（31日課金は28〜31日の間隔になり、30±4だと週次×4などのノイズも拾う）
5. 金額の許容 ±7.5%。**一定の段差は拒否ではなく値上げ**なので、新しい期間の提案にする
6. **3回以上**で提案（Plaid も3回で matured、Spade も3件以上、同じ閾値に独立に収束）。2回は「かもしれない」として出す

**`txn_allocation` は競合優位。** App Store / Google Play / キャリア決済の合算請求は**検出では原理的に解けない**。マネーフォワードME自身が「対応していない」と明記している。**2,480円のApp Store請求を3つのサブスクに1回手で分ければ、それを学習ルールとして再利用する。** これを出しているアプリがない。

## 7. 競合状況

- **マネーフォワードME のサブスクレポート**: プレミアム限定（¥540〜590/月、2025-08-05改定）。**先月の報告であって予測ではない**（「Adobeが9日後に6,480円」は出ない）。**App Store・キャリア決済は非対応**と公式に明記。年額サブスクは支払いが反映された翌月にようやく出る。検出はサービス許可リスト方式で動画配信中心
- **専用サブスク管理アプリ**（サブトラ、Subcut、Recur、サブマネ!、SubFlow、Bobby）: 台帳も突き合わせもない
- **市場は二分している。** (a) 台帳のないサブスク管理アプリ、(b) サブスクが有料の後ろ向きレポートになっている家計簿アプリ。**「取込済み台帳と突き合わせた、前向きのサブスク予測」をやっているものがない**
- **欲しいもの × 家計簿 × サブスク を統合したアプリは、出荷物としては存在しない。** 見つかったのは Notion テンプレートだけ（評価は1桁件数 = 需要の証拠であって、市場が満たされている証拠ではない）。「ほぼ確実に未開拓」とは言えるが「証明された」とは言えない（日本のApp Storeのロングテールはウェブ検索で網羅されない）

## 9. 根拠が薄いところ（正直に）

- **ストリーク等の損失フレーム機構について、自閉症の人を対象にした研究は1件も存在しない。** 良い悪いどちらの主張も外挿
- **年額に集約して目立たせる手法は未検証。** Gourville が検証したのは逆（売るために分割する）。本人の境界条件では**元の金額が大きいと効果が反転する**
- **「文面を変える」案は未検証。** 研究が変えたのは見た目
- 確認ダイアログ vs 取り消し の対照実験は見つからなかった（NN/g の経験則のみ）
- **認知アクセシビリティの平易な日本語ガイドは、同等の粒度のものが存在しない。** COGA の言語パターンは英語の形をしている（「二重否定を避ける」は日本語では `〜ないわけではない` や左方向の長い修飾が実際の問題）。デジタル庁のガイドブックは入門書。**UIが日本語なのでこれは実在する穴**で、自分で文面を試すしかない
- 自閉症の**成人**の色の好みについて: よく引かれる研究は**自閉症の男児29人**。成人の知見として扱えない
- 内受容感覚と金銭行動を結ぶ研究は見つからなかった。設計の根拠から外した
- Moneytree / Zaim に個人向けがないという結論は、**公開価格・サインアップが一貫して存在しないことからの推論**で、断られた記録ではない。確実にしたければ各社に1通メールすれば済む
- 調査環境から外部DNSが引けず、Stripe / RFC / 各クラウドの価格ページ・Next.js ドキュメント・マネーフォワード・Zaim の各ホストに直接アクセスできなかった。**GitHub と npm は到達できたので、Firefly III / Actual Budget / GnuCash / Maybe Finance のスキーマとアルゴリズムは実ソースで確認済み。** それ以外のベンダー情報は検索経由の抽出で、引用する前に確認が必要
